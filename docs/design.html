Card Maker

Design document — single-page tool for creating custom playing card sets.

Overview

Card Maker is a single, quietly styled page. There is no navigation, no routing and no sub-pages: content builds strictly from top to bottom as the user works through four steps. Everything runs in the browser; nothing is persisted.

Principles

  • One page, one flow. Four numbered steps, read and completed top to bottom.
  • Subtle visual design. Neutral palette, generous whitespace, no decoration that competes with the cards themselves.
  • Minimal implementation. Few components, few dependencies, no state beyond what the page needs.

Step 1 — Card format

The user picks a physical card format by clicking a schematic card. The formats are shown side by side as blank cards whose on-screen size is proportional to the real dimensions, so the differences are visible at a glance.

Step 2 — Layout

The layout defines which fields a card carries and how they are arranged. Layouts are presented as small schematic cards (rendered in the selected format's aspect ratio) with the field placeholders visible.

Step 3 — Frame design

A free-text prompt describes the desired visual style. From it the app builds a reference prompt and sends it to the OpenAI image API (gpt-image-1) to generate a decorative frame design — the shared visual identity of the whole card set.

The reference prompt combines:

  • the selected format (name and physical dimensions, portrait, full bleed),
  • the crop window: the generated 1024 × 1536 canvas is center-cropped to the format's aspect ratio, and the prompt states exactly which part of the image will be printed,
  • the selected layout's reserved content zones with concrete image coordinates (percent ranges of width and height, mapped through the crop window), which must stay visually quiet so content placed on top remains readable,
  • hard constraints: no text, no letters, no logos, no sample content, no characters,
  • the user's style prompt.

Layout geometry is the single source of truth: each layout defines its regions as percent rectangles of the card face, and the same rectangles drive both the prompt's content zones and the positioning of the editable fields in CardFace — so text and images entered later land exactly where the design keeps room for them.

After generation, a card theme is derived so the filled-in cards look cast from one mold: the average color of the frame's content zones is sampled on a canvas to produce a matching field background and a high-contrast ink color (dark ink on light zones, light ink on dark ones), and a language model picks the best-fitting typeface for the style prompt from a curated Google Fonts list. The theme is re-derived after every refinement.

A checkbox additionally requests a card back: a single symmetric ornamental composition covering the whole card, generated from the same style prompt. Front (and back, if requested) are rendered as previews directly below the prompt.

The API token is provided via the environment variable VITE_OPENAI_API_KEY (e.g. in an untracked .env.local) and is resolved at build time. Without a token the generate button is disabled and a short hint is shown.

Step 4 — Cards

Below the frame design, the user defines the actual cards of the set.

  • Image upload: one or more images at once; each image creates a new card in the selected format and layout, with the generated frame design as background and the image placed in the layout's artwork region.
  • Empty card: a card can also be created without an image; its artwork region stays empty and can be filled later by clicking it.
  • In-place editing: every field defined by the layout is edited directly on the card preview — there are no separate forms.
  • Cards can be removed individually.
  • PDF export: all cards are laid out on A4 sheets as a print-ready PDF. Each card is rendered at 300 dpi on a canvas using the same region geometry, typography and derived theme as the editor, placed at its exact physical size with crop marks. If a card back was generated, every front sheet is followed by a horizontally mirrored back sheet for long-edge duplex printing.

Technical notes

  • React + TypeScript + Vite, Tailwind CSS, shadcn/ui; deployed as a static site.
  • Card rendering is a single CardFace component: real aspect ratio via CSS aspect-ratio, all inner sizes in em relative to the card width, so one implementation serves schematic previews and full-size editable cards.
  • Uploaded images are held in memory as data URLs; there is no backend and no storage.

Non-goals

  • No accounts, saving or sharing.
  • No free-form layout editing — layouts are fixed templates.
